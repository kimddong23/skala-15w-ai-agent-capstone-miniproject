# 지연 최적화 측정 (에이전트 1회 분석)

측정: `eval/latency_bench.py` — 실제 MCP 서버 + 실제 Ollama(qwen2.5:3b fast / qwen3:8b quality), 대표 질의 5건
(U05·U03·U12·U08·U06, 각 최근 2주\~30일 점검)을 변형마다 새 프로세스에서 순차 실행. 모델 적재(웜업) 1회는 제외. 표: `eval/latency_table.py`.
원시 결과: `latency_v0..v5.json`.

| 변형 | 설정 | 평균 총(s) | 최대(s) | 분석 완료(s) | 작성 완료(s) | 검증 통과 | 1회 통과 | 평균 리포트 글자 |
|---|---|---|---|---|---|---|---|---|
| v0 | 기준선: analysis·writing 모두 qwen3:8b, JSON facts, 토큰 상한 없음, keep_alive 5m | 71.1 | 129.9 | 30.8 | 71.1 | 5/5 | 4/5 | 497 |
| v1 | (b)+(c) keep_alive 30m, num_predict 분석 220 / 작성 700 | 59.6 | 109.2 | 24.4 | 59.6 | 5/5 | 4/5 | 529 |
| v2 | v1 + (d) 압축 facts 텍스트 | 46.5 | 65.5 | 19.9 | 46.4 | 3/5 | 3/5 | 474 |
| v3 | v2 + (a) analysis 를 fast 모델로 | 27.2 | 31.5 | 13.2 | 27.2 | 5/5 | 5/5 | 414 |
| v4 | v2 + (a') analysis LLM 호출 생략(규칙 해석) 후 writing 1회가 해석 겸함 | 26.8 | 35.9 | 7.2 | 26.8 | 4/5 | 4/5 | 477 |
| **v5** | **채택 = v3 + 프롬프트에 "완결된 문장" 지시 추가 (기본값)** | **31.5** | **38.2** | 12.1 | 31.5 | **5/5** | **5/5** | 476 |

## 해석
- 기준선 71s → 채택안 31.5s (−56%). 가장 큰 기여는 analysis 를 8b → 3b 로 내린 것(v2→v3, −19s)과 facts 압축(v1→v2, −13s).
- **측정 잡음**: Ollama 를 다른 작업도 함께 쓰고 있어 같은 설정도 편차가 크다(v0 한 건은 130s, 재시도 포함). v0\~v2 가 앞쪽에서 돌아 경합이 더 컸을 가능성이 있다. 따라서 v3 vs v4 처럼 비슷한 값은 순위를 단정하지 않는다.
- keep_alive 는 한 프로세스 안에서는 효과가 없다(웜업 후 측정). 효과는 "유휴 5분 후 첫 질의"의 콜드 로드(관찰: route 1.5s → 5.4s, 8b 로드 수 초\~10초+)를 피하는 것으로, 본 표에는 반영되지 않았다.
- v2 의 통과율 3/5 는 속도 때문이 아니라 8b 작성기가 FACTS 에 없는 수치(6, 24, 24)를 인용해 validator 가 잡은 것이다(재시도 후에도 실패 → 템플릿 폴백). v4 의 1건(수치 "0")은 자명한 상수라 오탐으로 판단해 `0`, `24` 를 허용 상수로 추가했다.
- 채택(v5)의 trade-off: 3b 분석 문장이 8b 보다 얕다. v3 직후 샘플은 단어 나열식이어서 "완결된 문장" 지시를 추가했고(v5: 리포트 평균 476자로 회복) 검증 5/5 유지. 더 깊은 해석이 필요하면 `ANALYSIS_TIER=quality` 로 되돌리면 된다(이 경우 약 +10\~15s).
- 구조는 유지: analysis 노드는 그대로 존재하며(`MERGE_ANALYSIS=true` 로도 LLM 호출만 생략 가능), 설정은 환경변수(`ANALYSIS_TIER`, `MERGE_ANALYSIS`, `COMPACT_FACTS`, `NUM_PREDICT_*`, `LLM_KEEP_ALIVE`).
- 표본 5건이라 통계적 결론이 아니라 방향성 확인이다.
